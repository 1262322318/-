模块概述

变更管理定义了"如何安全地修改已有系统"，知识管理定义了"如何让系统越来越聪明"。两者结合形成项目的持续进化能力：每次变更不仅完成功能修改，还沉淀经验、更新模式库、触发健康检查，实现"越用越强"的正反馈循环。

核心设计 — 变更分类（6种类型）

代码类型典型场景推荐模式
CHG-01逻辑变更修改阈值、判定条件、计算公式A（直接修改）
CHG-02产品线扩展已有指标新增一条产品线B（草稿模式）
CHG-03字段新增DWS/ADS表加字段A
CHG-04Bug修复逻辑错误、数据异常A
CHG-05规则变更公共规则PUB-XXX调整B（影响面大）
CHG-06口径调整统计口径或维度变化B

核心设计 — 草稿模式（模式B）流程

模式B执行流程： 0. 参考确认 → grep搜索正式脚本定位参考段落 │ 1. 草稿生成 → sql_scripts/drafts/{原文件名}_{变更简称}_draft.sql │ 1.5 轻量自检（自动，用户无感） • 字段完整性核对（对照需求中的字段列表） • 指标完整性核对（对照需求中的子指标） • 目标表结构MCP验证 • 跨层字段一致性验证 │ 1.6 changelog即时记录（状态：🔄 草稿阶段） │ 2. 用户验证 → 提出修改意见 → Agent迭代修正 │ 3. 用户确认 → 手工合入正式脚本 │ 4. 用户告知"已合入" → Agent grep验证完整性 │ 5. 闭环：changelog更新为 ✅ 已完成

草稿隔离规则（防参考污染）

规则说明
存放位置统一在 sql_scripts/drafts/ 子目录
命名规范{原文件名}_{变更简称}_draft.sql
禁止参考生成新草稿时禁止引用drafts/下的文件
合法参考仅限正式脚本 + requirement.md + intake文档
合入后草稿保留不删除，便于追溯

核心设计 — 知识管理机制

1. 知识投喂（4种类型）

类型内容写入目标
表知识表名、业务语义、关键词、关联关系data_mapping.md + table_structures.md
规则知识业务规则、计算公式、分类条件business_rules.md
模式知识已完成需求的结构签名requirement_patterns.md
批量投喂一次性录入完整业务域多个文件

2. 知识健康检查（5维度）

维度检查内容
完整性表清单、关联关系、规则覆盖是否有缺失
一致性跨文件引用的表名/字段名是否一致
新鲜度最后命中时间、投喂频率
准确性MCP交叉验证（表结构vs知识库记录）
可用性关键词重叠度、模式库命中率

3. 自动改进提醒

每次需求完成（A7/B5）后，Agent主动回顾交互过程，如发现可优化点则输出改进建议。用户可选择"立即执行"/"记录到Backlog"/"忽略"。

优缺点分析

✅ 优势

  • 6种变更类型覆盖所有常见场景，每种有专属澄清维度
  • 草稿隔离彻底防止了"参考错误草稿"的系统性风险
  • 知识自学习形成正反馈（越用越准确）
  • 健康检查定期发现知识腐化问题
  • 经验教训记录表（etl_change_management.md末尾）防止同类错误重犯

❌ 局限

  • 知识库为单文件Markdown，无结构化索引能力
  • 健康检查需人工触发，不能定时自动执行
  • 模式库容量管理较粗放（≥20条才开始inactive）
  • 知识冲突检测缺乏语义理解（纯字符串比对）

待改进项

🔧 建议

  • P1：知识库结构化存储（如JSON/YAML），支持精准索引和查询
  • P1：定时健康检查（如每周一自动执行）
  • P2：知识版本管理（支持回滚到历史知识状态）
  • P2：知识冲突自动检测（新投喂 vs 已有知识的矛盾发现）
  • P3：知识图谱可视化（表-字段-规则-需求的关联网络）
