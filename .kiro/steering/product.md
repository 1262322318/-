# 产品概述

## ETL开发助手系统

ETL开发助手是一个能够自主执行ETL开发任务的AI系统，专门为海信内部数据工程需求设计。系统基于Apache Doris 2.1+数据库，遵循海信内部开发标准。

## 核心功能

1. **需求分析**：分析自然语言ETL需求，识别数据源、转换规则和目标结构
2. **模型设计**：基于Kimball维度建模理论设计数据仓库分层架构（ODS/DWD/DWS/ADS/DIM）
3. **脚本开发**：生成ETL脚本，实现数据提取、转换和加载流程
4. **脚本测试**：创建测试用例，验证脚本功能正确性
5. **文档生成**：自动生成符合海信标准的项目文档

## 设计原则

- **Kimball维度建模**：采用星型/雪花模式，支持事实表、维度表和缓慢变化维度
- **分层架构**：ODS存储原始数据，DWD清洗整合，DWS汇总计算，ADS业务应用，DIM维度管理
- **数据质量**：确保从原始数据到业务可用数据的完整链路质量一致性
- **性能优化**：支持批处理、并行处理、索引策略和物化视图
- **错误恢复**：实现重试逻辑、错误记录和回滚机制

## 适用场景

- 海信内部数据仓库建设
- ETL流程自动化开发
- 数据模型设计与优化
- 数据质量监控与改进

## 系统进化机制

本系统不局限于静态文件配置，支持以下自学习和持续进化方式：

| 进化方式 | 说明 | 当前状态 |
|----------|------|----------|
| 模式库自学习 | 每次需求完成后自动追加PAT模式签名 | ✅ 已实现 |
| 交互度量归因 | 每次交互后分析瓶颈，自动追加改进Backlog | ✅ 已实现 |
| 主动改进提醒 | A7/B5完成后主动发现并提出优化建议 | ✅ 已实现 |
| SQL模板提取 | 从已有SQL中学习可复用模式写入模板库 | ✅ 已实现（sql-template-extract技能） |
| MCP实时查询 | 通过table_metadata实时获取表结构，减少静态投喂 | ✅ 已实现 |
| 反馈闭环 | 全局监听+定期复盘+改进优先级排序 | ✅ 已实现 |
| 知识健康检查 | 5维度体检+评分+修复引导 | ✅ 已实现 |
| 外部技能引入 | 从社区/团队导入新技能定义（需人为确认可行性） | 🔮 规划中 |
| 对话样本训练 | 积累对话样本用于优化澄清问题和判定阈值 | 🔮 规划中 |
| 规则自动发现 | 从多次需求中自动提炼新的公共规则 | 🔮 规划中 |

**进化原则**：每个新增能力都必须服务于"让项目越来越强"这个目标。引入新能力前需评估：是否降低交互次数？是否提高输出质量？是否减少人工干预？

## 快速问答模式

当用户提出简短问题（如"PG00002是什么字段？"、"PUB-003的冰箱条件是什么？"、"004和005的依赖关系？"）时，Agent直接从知识库中检索回答，**不启动需求处理流程**。只有当用户明确表达"新需求/修改需求/投喂知识"等意图时才激活对应技能。

## 反馈自动捕获模式（全局，针对试用期）

为减少测试人员负担，Agent在所有对话中**被动监听**用户的吐槽和建议信号，自动记录到 `.kiro/data/feedback-records/`，无需用户手动操作。

### 信号词触发（用户说出以下任一时）

**抱怨/问题信号**：
- "不好用"、"太麻烦"、"卡壳"、"傻"、"不对劲"
- "bug"、"出错了"、"报错"、"不能用"、"卡死"
- "太慢"、"太久"、"等半天"

**建议/期望信号**：
- "希望能"、"要是能"、"如果可以"
- "建议"、"我觉得应该"、"最好"

**主动反馈信号**：
- "我吐槽"、"反馈一下"、"提个意见"、"给个建议"

### Agent捕获行为
1. **不打断当前任务**：用户说"希望能跑一下SQL"时，继续完成当前任务
2. **背景静默记录**：把用户原话和上下文写入 `.kiro/data/feedback-records/{YYYYMMDD}-{HHMMSS}-issue.md`
3. **当前任务结束后追问1句**（且仅1句）：
   ```
   刚才你提到"XXXX"，我已记录。能否补充一句具体场景？（也可跳过）
   ```
4. **用户跳过/沉默30秒** → 不再追问，记录已保存即可

### 不捕获的场景
- 用户在确认阶段说"不对/调整" → 这是流程内修正，不是反馈
- 用户问技术问题中包含"bug"等词 → 通过上下文判断是否真的是抱怨
- 用户引用的别人的话 → 不捕获

### 一键导出
试用期结束（或用户主动要求）时，用户说"导出反馈"，Agent调用 `feedback-collector` 技能把所有反馈+度量数据打包到项目根目录的单个markdown文件，方便发送给项目负责人（独立电脑无git/云场景）。

## 技术栈与环境

### 核心技术栈
- **Apache Doris 2.1+**：主要数据存储和计算引擎（MPP架构，物化视图，兼容标准SQL）
- **Kimball维度建模理论**：星型/雪花模式，ODS/DWD/DWS/ADS/DIM五层架构
- **缓慢变化维度（SCD）**：支持Type 1/2/3处理策略
- **海信内部开发规范**：命名约定、代码结构、文档头格式

### 开发环境要求
- Apache Doris 2.1+ 数据库环境
- 支持SQL开发工具
- 版本控制系统（Git）

### 测试框架
- 单元测试：验证单个ETL组件功能
- 集成测试：验证数据流转和转换逻辑
- 性能测试：评估ETL脚本执行效率

### 技术约束
1. 所有数据模型必须与Apache Doris 2.1+兼容
2. 大数据量场景需支持批处理和并行处理
3. 所有ETL脚本必须包含错误处理和日志记录
4. 数据质量检查需在转换过程中实现

### 部署与运维
- 海信内部数据平台环境，Apache Doris集群部署
- 调度系统集成（如Airflow、DolphinScheduler）
- ETL执行日志记录、数据质量监控、性能指标收集

### 调度参数规范
- `${GP_START_DT}`：调度系统传入，代表脚本执行日期的前一天（昨天），格式 yyyymmdd
- 取上月年月：`DATE_FORMAT(date_sub('${GP_START_DT}', interval 1 month), '%Y%m')`
- 取当月年月：`DATE_FORMAT('${GP_START_DT}', '%Y%m')`
- 取上月1日：`STR_TO_DATE(CONCAT(DATE_FORMAT('${GP_START_DT}', '%Y-%m'), '-01'), '%Y-%m-%d')`
