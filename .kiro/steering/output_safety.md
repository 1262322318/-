# 输出安全规则（防乱码 + 分段输出）

## 概述

本文件定义Agent在输出长内容（SQL脚本、文档等）时的强制分段规则和乱码恢复协议。全局生效，适用于所有链路（新建链路A、变更链路B、直接修改等）。

## 一、强制分段输出规则

### 触发条件

| 场景 | 判定 | 处理 |
|------|------|------|
| 单个SQL脚本预估 ≥ 120行 | 必须分段 | 按下方策略拆分 |
| 单次回复中包含 ≥ 2个独立SQL段落 | 必须分段 | 每个段落独立输出 |
| 单次回复预估总字符数 ≥ 4000字 | 建议分段 | 提示用户选择 |
| 单个SQL脚本 < 120行 | 豁免 | 可一次性输出 |

### 分段策略（SQL脚本）

**标准三段式**（适用于大多数DWS层脚本）：

| 段落 | 内容 | 预估行数 |
|------|------|----------|
| 第一段 | DELETE语句 + INSERT字段列表 + 基础CTE（产品线映射、型号信息） | 50-80行 |
| 第二段 | 数据CTE（销量、规划量、库存等）+ 最终SELECT | 50-80行 |
| 第三段（如有） | 第二个zhibiao_type的完整逻辑（独立DELETE+INSERT+CTE+SELECT） | 50-80行 |

**多指标场景**：每个zhibiao_type/独立指标作为独立段落，不合并输出。

### 分段输出交互规范

每段输出后，Agent必须暂停并提示：
```
--- 第X段结束（共N段）---
请确认本段无乱码后回复"继续"，我输出下一段。
```

用户回复"继续"后才输出下一段。禁止自动连续输出。

### 分段衔接规则

1. 第二段开头用注释列出第一段中定义的CTE名称，确保衔接正确：
```sql
-- 承接第一段CTE：jiguang_productline, jiguang_model, all_model
```
2. 禁止在分段边界处截断：
   - 一个完整的CASE/WHEN块
   - 一个完整的子查询（括号内）
   - 一个完整的CTE定义
3. 每段必须是语法上可独立阅读的完整块（虽然不能独立执行）

### 写入文件时的分段

当使用fs_write写入文件时，同样遵循分段规则：
- 第一次fs_write写入前半部分
- 用fs_append追加后半部分
- 每次写入/追加后，Agent读取文件确认内容完整无乱码

## 二、乱码恢复协议

### 触发条件

用户反馈以下任一信号：
- "乱码"、"看不懂"、"乱了"、"重新来"、"这段有问题"
- 对话中出现明显的编码异常字符

### 恢复步骤

1. **立即停止当前输出**，不继续生成后续内容
2. **确认损失范围**：
   ```
   【乱码恢复】
   请确认：前面第1~N段中，哪些是正常的？从第几段开始出现乱码？
   ```
3. **锚定恢复点**：
   - 前面段落正常 → 只重新生成乱码段
   - 全部乱码 → 从第一段重新开始
4. **重新生成前必须做的事**：
   - 重新读取需求文档对应段落（不依赖上下文记忆）
   - 列出"本段应包含的关键要素"（3-5条），让用户确认
   - 缩短本段长度（比原来减少20%）
5. **输出恢复确认**：
   ```
   【准备重新输出第N段】
   
   本段包含：
   1. [要素1]
   2. [要素2]
   3. [要素3]
   
   确认后输出。
   ```

### 恢复禁止行为

- 禁止"从零重写整个脚本"（除非用户明确要求）
- 禁止跳过已确认段落重新生成
- 禁止在恢复时改变已确认段落中的逻辑（CTE名称、字段顺序、变量名）
- 禁止将恢复当作"优化机会"去修改之前已确认的内容

## 三、禁止使用Shell命令修改文件内容

### 规则（强制）

**禁止使用PowerShell/CMD命令读取或修改含中文内容的文件。**

所有文件内容的读取、替换、写入必须使用专用工具：
- 读取：`read_file` / `read_files` / `read_code`
- 替换：`str_replace`
- 写入：`fs_write` / `fs_append`

Shell命令（execute_pwsh）仅限用于以下不涉及文件内容的操作：
- 创建目录（New-Item -ItemType Directory）
- 移动/重命名文件（Move-Item）
- 删除文件（Remove-Item）
- 检查文件是否存在（Test-Path）
- 列目录（Get-ChildItem）

### 原因

PowerShell 5.x 的 `Get-Content` + `Set-Content` 在处理UTF-8中文文件时存在编码转换问题（默认写入UTF-8 with BOM，且管道传输中可能触发GBK编码转换），导致中文变为乱码。此问题在当前Windows环境下无法可靠修复。

### 违规判定

如果Agent使用了 `Get-Content -replace Set-Content`、`Out-File`、管道重定向（`>`）等方式修改了含中文的文件，且导致乱码，Agent必须立即用 `fs_write` 重写该文件恢复正确内容。

## 四、适用范围

| 场景 | 是否适用 |
|------|----------|
| 链路A - A6 SQL生成 | ✅ |
| 链路B - B4 执行修改（模式B草稿生成） | ✅ |
| 链路B - B4 执行修改（模式A直接修改） | ✅（修改内容≥120行时） |
| 需求文档生成（requirement.md） | ✅（文档≥4000字时） |
| 对话中的分析说明 | ❌（不适用，正常输出即可） |
| 短SQL片段展示（<120行） | ❌（豁免） |
