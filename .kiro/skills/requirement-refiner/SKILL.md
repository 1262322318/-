# 技能：需求精化（Requirement Refiner）

## 触发词

- "精化需求"
- "生成PRD"
- "refine"
- converter 完成后自动提示

## 功能描述

将 converted 文档（MRD级别）精化为 refined 文档（PRD级别），包含字段级映射、确定度标记、参考指令和禁止行为，使后续 SQL 生成阶段能够精确执行。

**定位**：converter 保持原意做格式转换，refiner 做语义增强（映射表字段、标注确定度、生成参考指令）。

## 触发条件

| 场景 | 触发方式 |
|------|----------|
| converter 完成后 | Agent自动提示"是否精化" |
| 用户引用 converted 文件并说"开始处理" | 自动触发 refiner |
| 用户说"精化需求"/"生成PRD" | 手动触发 |
| 用户引用 refined 文件 | 跳过 refiner，直接进入正式流程 |
| 用户说"直接改"/"跳过精化" | 跳过 refiner，走原流程 |

## 输入与输出

| | 输入 | 输出 |
|--|------|------|
| 文件 | `intake/{ID}/converted/*.md` | `refined/{ID}/*_prd.md` |
| 级别 | MRD（业务语言，模糊引用） | PRD（字段级映射，确定度标记） |
| 用户参与 | 无（已粘贴完成） | 确认待澄清项 |

## 模板选择规则

| 条件 | 选择模板 | 文件位置 |
|------|----------|----------|
| 新建需求 + 指标数=1 | 新建-单指标 | `refined/templates/refined_new_single.md` |
| 新建需求 + 指标数≥2 | 新建-多指标 | `refined/templates/refined_new_multi.md` |
| 变更需求（任何类型） | 变更 | `refined/templates/refined_change.md` |

判定依据：
- converted 文档 front-matter 中 `初步判断` 字段
- 文档中独立指标的数量（有独立计算公式/独立筛选条件的算独立指标）

## 执行流程

### 步骤1：读取与解析

1. 读取 converted 文档全文
2. 提取指标列表（每个有独立定义的指标）
3. 提取公共规则（适用所有指标的筛选条件、产品范围）
4. 识别模糊引用（"同视像"、"同XX"、"参考XX"）

### 步骤2：模式匹配

1. 读取 `requirement_patterns.md`
2. 对每个指标匹配已有模式（关键词重叠度≥60%）
3. 确定参考需求和参考脚本
4. 确定依赖关系和处理顺序

### 步骤3：表字段映射（MCP查询）

对 converted 文档中的每个业务描述，通过 MCP 查询字段列表映射到实际字段（用 Q1，查询范式与失败降级规则见 `.kiro/skills/etl-requirement/mcp-table-metadata.md` 契约；本文件不再内嵌 SQL）。

映射规则：
| 业务描述中的关键词 | 匹配 column_comment | 输出 |
|-------------------|--------------------|----- |
| 产品公司 | 包含"公司"或"company" | `{column_name}`（备注：{comment}） |
| 产品小类 | 包含"小类"或"small" | `{column_name}`（备注：{comment}） |
| 品牌 | 包含"品牌"或"brand" | `{column_name}`（备注：{comment}） |
| 上市时间 | 包含"上市"或"market" | `{column_name}`（备注：{comment}） |
| 退市时间 | 包含"退市"或"delist" | `{column_name}`（备注：{comment}） |
| 产品线 | 包含"产品线"或"line" | `{column_name}`（备注：{comment}） |
| 生命周期 | 包含"生命周期"或"lifecycle" | `{column_name}`（备注：{comment}） |
| 内销/外销 | 包含"内销"或"外销"或"domestic"或"export" | `{column_name}`（备注：{comment}） |

匹配不上的标注 `【待确认-MCP未匹配】`，列入待澄清项。

### 步骤4：确定度标注

| 条件 | 标注 |
|------|------|
| 需求文档给出精确枚举值（如IN列表） | 确定 |
| 需求文档给出明确公式/阈值 | 确定 |
| MCP查表验证字段存在且备注匹配 | 确定 |
| 需求文档写"同XX"（已展开为具体逻辑） | 确定 |
| 需求文档写"同XX"（无法展开） | 待确认 |
| 需求文档该项为空或[待澄清] | 待确认 |
| MCP查表未找到对应字段 | 待确认 |

### 步骤5：展开模糊引用

| 模糊引用 | 展开方式 | 展开后要求 |
|----------|----------|-----------|
| "同视像" | 读取视像对应需求的 requirement.md + SQL脚本，提取具体逻辑 | 必须包含字段名、表名、条件值 |
| "同XX指标" | 读取XX指标的 requirement.md 对应段落 | 必须包含字段名、表名、条件值 |
| "参考XX" | 明确参考的脚本名 + grep定位方式 | 必须有脚本文件名+定位关键词 |
| "需线下提供" | 标注为待确认，列入待澄清项 | 给出AI默认假设 |

**强制规则**：展开后的内容必须包含具体的字段名、表名、条件值。不允许展开后仍然是模糊描述。

### 步骤6：差异分析（有参考需求时）

1. 读取参考需求的正式SQL脚本（非drafts）
2. 读取参考需求的 requirement.md
3. 逐项对比，生成差异清单：
   - 表不同 → 记录字段映射（参考对象字段 vs 本需求字段）
   - 筛选条件不同 → 记录新旧对比
   - 新增字段/规则 → 记录为"新增规则"
   - 参考对象有但本需求不需要 → 记录为"不适用规则"

### 步骤7：生成禁止行为

根据以下来源生成禁止行为清单：
1. `etl_change_management.md` 第六节"经验教训记录"
2. 本需求的特点（如有精确枚举→禁止LIKE）
3. 历史同类需求的常见错误

最少生成3条禁止行为。

### 步骤8：组装输出

按选定的模板结构组装 refined 文档，写入 `refined/{需求目录名}/` 目录。
需求目录名与 intake 中的目录名保持一致（如 `20260528-laser-product-efficiency`）。

### 步骤9：质量自检

| 检查项 | 通过条件 | 不通过处理 |
|--------|----------|-----------|
| 所有"同XX"已展开 | 文档中无"同XX"模糊引用 | 重新展开 |
| 关键字段已映射 | 产品范围/产品线/时间字段都有字段名 | MCP补查 |
| 确定度已标注 | 每个规则项都有确定度标记 | 补标注 |
| 禁止行为已生成 | 至少3条禁止行为 | 从经验教训中补充 |
| 参考对象已定位 | 有具体脚本名+grep定位方式 | 补充定位 |
| 差异清单完整 | 表/字段/规则三个维度都有对比 | 补充对比 |

### 步骤10：向用户展示确认

```
【需求精化完成】

已生成 PRD 文档：refined/{目录}/{文件名}_prd.md

关键信息确认：
1. 识别到 {N} 个指标：{列表}
2. 框架参考：{参考需求ID}
3. 已映射字段：{N}个（通过MCP验证）
4. 待确认项 {M} 个：
   - {待确认项1}
   - {待确认项2}
   ...

请确认以上信息，或补充待确认项。确认后可进入正式开发流程。
```

用户确认后：
- 更新 refined 文档的确认记录
- 将待确认项的用户回答更新到文档中（确定度改为"确定"）
- 进入正式流程（链路A或链路B）

## 与正式流程的衔接

### 新建需求（链路A）

refined文档让每个步骤执行更快，但**不跳过任何步骤**：
- A1（依赖识别）：从 refined 的 front-matter 中读取，输出确认
- A2（需求澄清）：确认 refined 中的待确认项（如无则输出"无需澄清"确认）
- A3（数据表匹配）：refined 已完成表映射，输出让用户确认
- A4a（模型骨架）：从refined提取骨架+MCP校验，输出让用户确认
- A4b（字段设计）：从refined读取字段设计，输出让用户确认
- A5（最终确认）：基于 refined 文档汇总
- A6a（SQL骨架）：输出CTE框架让用户确认
- A6b（SQL填充）：读取 refined 文档生成

### 变更需求（链路B）

refined文档让每个步骤执行更快，但**不跳过任何步骤**：
- B1（定位已有资产）：从refined读取参考对象和脚本，输出确认
- B2（变更澄清）：refined 的差异清单已覆盖，输出确认
- B3（影响分析）：从refined读取下游影响，输出确认
- B3.5（交付模式）：refined 已给出建议，输出确认
- B4（执行修改）：按 refined 的差异清单和字段映射生成

### AI读取refined文档的规则

1. **每次生成SQL前**：重新读取 refined 文档的"公共规则"section（不依赖上下文记忆）
2. **生成某个指标时**：读取该指标的完整section（包括规则速查）
3. **生成变更SQL时**：逐条对照差异清单，每处理一条差异在心中打勾
4. **遇到"待确认"标记时**：按"AI默认假设"处理，在SQL注释中标注 `-- [待确认] {说明}`

## 文件命名规范

| 场景 | 命名格式 | 示例 |
|------|----------|------|
| 新建-单指标 | `{日期}_{指标名}_prd.md` | `2026-05-28_新品规划命中率_prd.md` |
| 新建-多指标 | `{日期}_{需求名}_prd.md` | `2026-05-28_激光产品效率管理_prd.md` |

## 注意事项

1. refiner 只做"语义增强"，不改变需求原意
2. 所有MCP查询结果写入refined文档，便于用户验证
3. 待确认项必须给出"AI默认假设"，用户可直接确认或修正
4. refined 文档是后续SQL生成的第一输入源，优先级高于经验
5. 用户可以手工编辑refined文档，Agent尊重用户修改
6. 模板文件位于 `refined/templates/` 目录下
