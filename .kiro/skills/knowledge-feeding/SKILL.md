# 知识投喂技能（含智能校验引擎）

## 触发词
用户说以下任意一种时激活本技能：
- "投喂知识"、"录入表信息"、"注册表"
- "添加规则"、"录入规则"
- "录入需求模式"、"注册需求"
- "投喂"、"教你一下"

## 技能说明
本技能用于规范化地向助手投喂业务知识。每条信息录入后，Agent会执行**智能校验**（格式检查+推理反馈），确保数据准确完整后才写入steering文件。

**核心原则：准确性优先于速度。每条录入必须经过校验→反馈→用户确认三步才写入。**

---

## 执行流程

### 第一步：确定投喂类型

**Agent输出**：
```
请选择要投喂的知识类型：

1. 📊 表知识（表名、字段、关联关系）
2. 📐 规则知识（业务规则、计算公式、分类条件）
3. 🧩 模式知识（已完成的需求结构、依赖关系）
4. 📦 批量投喂（一次性录入完整业务域）

请选择（1/2/3/4）。
```

## 类型1：表知识投喂

### 1.1 基本信息采集

**MCP优先原则**：已接通PostgreSQL MCP（table_metadata表），表结构字段信息可通过MCP实时查询，**不再需要用户手动投喂字段列表**。投喂重心转向：业务语义、触发关键词、关联关系、使用场景。

逐项询问，每项等用户回答：

| 序号 | 问题 | 格式要求 |
|------|------|----------|
| 1 | 表的完整名称？ | `库名.表名`（如 ods.xxx） |
| 2 | 属于哪一层？ | ODS/DWD/DWS/ADS/DIM |
| 3 | 存什么数据？（业务语义） | 一句话描述这张表的业务用途 |
| 4 | 触发关键词？ | 逗号分隔的关键词列表 |
| 5 | 使用场景？ | 哪些指标/需求会用到这张表 |

### 1.2 核心字段采集（MCP优先）

**优先方式**：Agent 自动通过 MCP 查询字段列表（用 Q1，见 `.kiro/skills/etl-requirement/mcp-table-metadata.md` 契约；本文件不再内嵌 SQL）：

- 如果MCP查询成功：向用户展示字段列表，请用户标注哪些是**核心字段**（常用于JOIN/WHERE/SELECT的字段）
- 如果MCP查询无结果（表未录入metadata）：退回手动模式，请用户提供字段信息

手动模式格式：
```
请列出核心字段（常用的即可，不需要全部）。

格式：字段名 | 类型 | 说明
示例：
yearmonth | VARCHAR(6) | 统计年月
matnr | VARCHAR(40) | 物料编码
sale_qty | DECIMALV3(20,4) | 销量

请输入（输入"完成"结束）：
```

也支持直接粘贴DDL，Agent自动解析。

### 1.3 关联关系采集

```
这张表与其他表有关联关系吗？

格式：本表字段 → 关联表.关联字段 | 说明
示例：matnr → dw.dim_product_base_info_dd.product_code | 物料关联主数据

请输入（输入"无"或"完成"结束）：
```

### 1.4 智能校验（Agent自动执行）

用户输入完成后，Agent执行以下校验并输出反馈：

```
【智能校验报告】

✅ 通过项：
- 表名格式正确（库名.表名）
- 分层与库名一致

⚠️ 建议项：
- [具体建议，如"字段sale_qty使用了DECIMAL，建议改为DECIMALV3(20,4)（Doris 2.1+推荐）"]
- [具体建议]

❓ 推理反馈（请确认）：
- [推理1，如"我注意到您录入的matnr字段与已有的ods管报表的matnr含义相同，是否是同一个物料编码？"]
- [推理2，如"您录入的表属于ODS层，通常ODS表会有对应的DWD层清洗表，是否需要一并录入？"]

❌ 错误项（必须修正）：
- [错误，如"关联目标表 dw.xxx 在当前知识库中不存在，请确认表名是否正确"]

请根据以上反馈修正，或确认无需修改。
```

### 1.5 推理反馈规则（Agent内部逻辑）

Agent在校验时执行以下推理：

| 推理类型 | 触发条件 | 反馈内容 |
|----------|----------|----------|
| 关联链延伸 | 用户录入A→B关联，B→C已存在 | "B表还关联了C表，A是否也需要通过B到达C？" |
| 产品线覆盖 | 用户录入了某产品线的表，但同类其他产品线未录入 | "冰箱的表已录入，冷柜是否也有类似的表？" |
| 命名一致性 | 字段名与已有表的同义字段命名不同 | "已有表中类似字段叫sale_qty，您的是sales_quantity，是否同一含义？" |
| 分层完整性 | 录入了DWS表但无对应ADS表 | "通常DWS明细表有对应ADS结果表，是否需要补充？" |
| 关键词重叠 | 新关键词已被其他表使用 | "关键词'销量'已映射到ods管报表，新表也用这个关键词会产生歧义，建议用更具体的词" |
| 字段类型建议 | 使用了非标准类型 | "建议使用DECIMALV3替代DECIMAL（Doris 2.1+推荐）" |
| 缺失字段推理 | 表描述提到某业务但字段中没有对应列 | "您描述这是销量表，但字段中没有看到时间字段，是否遗漏了？" |

### 1.6 用户确认后写入

用户确认"没问题"后：
- 追加到 `data_mapping.md` 的关键词→表映射
- 追加到 `table_structures.md` 的对应分层章节
- 关联关系追加到 `data_mapping.md` 的关联关系总览

写入后输出：
```
✅ 已写入。当前知识库状态：
- 表总数：[N]张
- 本次新增：1张
- 关联关系：[N]条
```

同时追加一条记录到 `.kiro/data/feeding-log.md`：
```
| {当前时间} | 表知识 | {库.表名} - {描述} | data_mapping.md + table_structures.md | {用户名} |
```

## 类型2：规则知识投喂

### 2.1 规则基本信息

| 序号 | 问题 |
|------|------|
| 1 | 规则名称？ |
| 2 | 适用范围？（哪些指标/产品线） |
| 3 | 触发关键词？ |
| 4 | 优先级？（P0必须/P1建议/P2按需） |

### 2.2 规则内容

```
请描述规则内容，支持以下方式：
A. 自然语言描述（我来转换为SQL）
B. 直接给SQL片段
C. 判定表格（条件→结果）
```

### 2.3 智能校验

```
【规则校验报告】

✅ 通过项：
- 规则编号连续（PUB-0XX）
- 优先级合理

⚠️ 建议项：
- [如"CASE WHEN没有ELSE兜底，建议补充默认值"]
- [如"WHERE条件可能导致全表扫描，建议加分区过滤"]

❓ 推理反馈（请确认）：
- [如"这条规则的条件与PUB-003有部分重叠（都涉及产品大类='控温储藏类产品'），当两者同时满足时以哪个为准？"]
- [如"您的规则只覆盖了内销场景，外销是否也适用？"]
- [如"规则中引用了字段PG00002，这个字段在dim_productmodel表中，是否需要先确认该表已录入？"]

❌ 错误项：
- [如"规则中引用的表xxx不在当前知识库中"]
```

### 2.4 确认后写入

追加到 `business_rules.md`，分配编号 PUB-0XX。

同时追加一条记录到 `.kiro/data/feeding-log.md`：
```
| {当前时间} | 规则知识 | PUB-0XX: {规则名称} | business_rules.md | {用户名} |
```

## 类型3：模式知识投喂

### 3.1 需求信息采集

| 序号 | 问题 |
|------|------|
| 1 | 指标名称？ |
| 2 | 触发关键词？ |
| 3 | 涉及哪些表？ |
| 4 | 分层路径？ |
| 5 | 应用哪些公共规则？ |
| 6 | 复杂度？（简单/中等/复杂） |
| 7 | 依赖哪些其他指标？ |

### 3.2 智能校验

```
【模式校验报告】

✅ 通过项：
- 模式编号连续
- 分层路径合理

❓ 推理反馈：
- [如"您提到涉及dim_productmodel表，但触发关键词中没有'产品型号'，是否需要补充？"]
- [如"您标注依赖'在销型号数'，但PAT-003的输出表是dws_sale_model_detail_dd，您的涉及表中是否应该包含它？"]
- [如"复杂度标为'简单'，但涉及4张表+3条规则，建议调整为'中等'"]
```

### 3.3 确认后写入

追加到 `requirement_patterns.md`。

## 类型4：批量投喂

### 4.1 业务域概述

```
请描述您负责的业务域：
1. 业务域名称？
2. 大约涉及几张核心表？
3. 有几条公共规则？
4. 已完成几个需求？
```

### 4.2 支持的输入方式

```
批量投喂支持以下输入方式（可混合使用）：

A. 逐条录入（我引导您一张表一张表录）
B. 粘贴DDL（CREATE TABLE语句，我自动解析）
C. 粘贴已有SQL脚本（我从中提取表、字段、关联、规则）
D. 粘贴文档/Excel内容（我解析结构化信息）

推荐：先用方式B/C快速导入，再用方式A补充关键词和业务描述。
```

### 4.3 批量录入后的整体校验

批量录入完成后，Agent执行一次**全面交叉验证**：

```
【批量投喂完整性报告】

📊 录入统计：
- 表：[N]张（ODS:[n] DWD:[n] DWS:[n] ADS:[n] DIM:[n]）
- 规则：[N]条
- 模式：[N]个

✅ 完整性检查：
- 所有关联关系的目标表均已录入
- 所有规则引用的表均已录入
- 所有模式的依赖均可追溯

⚠️ 建议补充：
- [如"有3张DWS表没有对应的ADS结果表"]
- [如"规则PUB-003引用了字段PC00001，但该字段未在任何表的核心字段中出现"]

❓ 推理反馈：
- [如"您录入了5条产品线相关规则，但只覆盖了冰箱/冷柜/洗衣机，空调和视像是否也需要？"]
- [如"模式PAT-001和PAT-002的触发关键词有3个重叠，可能导致误匹配"]

请逐项确认或补充。
```

## 投喂计数器（用于触发自动健康检查）

Agent在每次投喂完成后，在 `.kiro/data/feeding-counter.json` 中记录：

```json
{
  "total_feeds": 0,
  "last_health_check": "2026-05-15",
  "feeds_since_last_check": 0,
  "tables_added": 0,
  "rules_added": 0,
  "patterns_added": 0
}
```

当 `feeds_since_last_check >= 5` 时，Agent在下次投喂结束后提醒：
```
⚠️ 自上次健康检查以来已累计投喂[N]条数据，建议执行一次知识库健康检查。
是否现在执行？（是/否/稍后）
```

## 注意事项
- 通过 `#knowledge-feeding` 手动引用激活
- 每条录入必须经过：采集 → 校验 → 推理反馈 → 用户确认 → 写入
- 准确性优先于速度，宁可多问一轮也不写入有疑问的数据
- 批量投喂结束后强制执行一次整体校验
