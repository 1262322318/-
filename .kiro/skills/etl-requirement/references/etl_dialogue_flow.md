# ETL需求处理对话流程（v3.0 骨架先行 + 多指标编排）

## 概述

本文档定义ETL智能辅助工具的对话流程。v3.0核心变化：
1. **骨架先行**：A4拆为模型骨架（A4a）+ 字段设计（A4b），A6拆为SQL骨架（A6a）+ 填充逻辑（A6b）
2. **多指标编排**：新增A0步骤，多指标同领域场景自动触发
3. **refined快速校验**：从"跳过"改为"自动提取+快速确认"
4. **反例澄清**：A2增加排除条件主动追问
5. **动态裁剪**：根据复杂度判定自动合并/拆分步骤

**核心原则：每一步必须获得用户明确确认后才能进入下一阶段。禁止跳步。**

## 对话状态机总览

```
状态1（初始）→ 状态2（接收+关键词提取）→ 状态2.5（需求分类判定）
                                              │
                              ┌────────────────┼────────────────┐
                              ▼                                  ▼
                    链路A：新建需求流程                 链路B：变更需求流程
                    [A0]→A1→A2→A3→A4a→A4b→A5→A6a→A6b→A7    B1→B2→B3→B3.5→B4→B4.5→B5→B6
                     ↑                         ↑
                 多指标触发              简单需求可合并
```

## 复杂度判定规则（全局，A1之前执行）

| 判定条件 | 复杂度 | 步骤策略 |
|----------|--------|----------|
| 单指标 + 不新建DWS（只聚合ADS）| 简单 | A4a+A4b合并，A6a+A6b合并，A5可跳过 |
| 单指标 + 单产品线 + 有参考需求 | 简单 | 同上 |
| 单指标 + 多产品线 或 新建DWS | 复杂 | 全部拆分执行 |
| 多指标（≥2个）+ 同领域 | 复杂+编排 | 触发A0，按批次执行 |
| 多指标 + 不同领域 | 拆分 | 拆为独立需求分别走链路A |

## 状态1：初始状态

**触发条件**：用户发起ETL需求相关请求
**Agent行为**：
1. 简短问候
2. 请求用户描述需求

**输出模板**：
```
请描述您的ETL需求。我会根据需求类型（新建/变更/修复）走不同的处理流程。

提示：
- 新建指标：请描述指标名称、业务含义、涉及产品线
- 修改已有指标：请说明需求ID或指标名称 + 具体变更内容
- Bug修复：请说明哪个指标、什么问题
```

**退出条件**：用户提供了需求描述 → 进入状态2

## 状态2：需求接收（关键词提取）

**触发条件**：用户提供了需求描述
**读取规则**：`etl_analysis_clarification.md`
**Agent行为**：
1. 从用户输入提取关键词（业务词/技术词/时间词/指标词）
2. 识别是否提及已有需求ID或指标名称
3. 识别动词类型（新建类/变更类/修复类）
4. **识别指标数量**：用户提到几个独立指标？是否属于同领域？

### intake 文件快速接入规则
如果用户通过 `#` 引用了 `intake/converted/` 下的标准化 .md 文件：
1. 直接读取该文件内容作为需求输入
2. 文件中已填充的字段（非 `[待澄清]`）视为"用户已确认的事实"
3. 文件中标记为 `[待澄清]` 的字段，在后续澄清阶段（A2/B2）重点询问
4. 跳过状态1（初始问候），从状态2的关键词提取开始
5. 后续步骤仍然按顺序执行，不跳过（即使信息充分，A2仍需输出"无需澄清"让用户确认）

### refined 文件快速接入规则（优先级高于 converted）
如果用户通过 `#` 引用了 `refined/` 下的 *_prd.md 文件：
1. 直接读取该 refined 文件作为需求输入（PRD级别，已含字段映射和确定度标记）
2. 跳过状态1（初始问候），从状态2开始
3. **链路A和链路B的每个步骤仍然按顺序执行，不跳过任何步骤**
4. refined的优势体现为"每步更快"（从refined提取信息而非从头分析），而非"跳步"
5. 变更需求：同样按B1→B2→B3→B3.5→B4→B5顺序执行，每步从refined提取信息
6. refined中的"待确认项"在对应阶段重点确认

**核心原则：refined提供的是更高质量的输入，不是跳步的理由。不存在任何"跳过"逻辑。**

**refined通道下各步骤的简化形式**（步骤不可省，输出可简化）：
| 步骤 | 无refined时 | 有refined时 |
|------|------------|-------------|
| 状态2关键词提取 | 从用户文本提取 | 从refined front-matter直接读取，输出确认 |
| 状态2.5分类判定 | 按规则判定 | 从refined type字段读取，输出确认 |
| A1依赖识别 | 分析上下游 | 从refined读取依赖关系，输出确认 |
| A2需求澄清 | 提问3-8个问题 | "refined已全部澄清，无需追问。确认？"（或确认少量待确认项） |
| A3数据表匹配 | 从关键词推导表 | "从refined读取已验证的表组合：[列表]。确认？" |
| A4a模型骨架 | 从零设计骨架 | "从refined提取骨架5要素并MCP校验：[结果]。确认？" |
| A4b字段设计 | 展开字段列表 | "从refined读取字段设计：[列表]。确认？" |
| A5最终确认 | 增量汇总 | "refined全部确认通过，无修正项。确认进入SQL生成？" |
| A6a SQL骨架 | 输出CTE框架 | 输出CTE名称+一句话用途，用户确认 |
| A6b SQL填充 | 逐段生成 | 逐段生成（同标准流程） |
| A7文档+沉淀 | 生成全套产物 | 生成全套产物（同标准流程） |

### converter → refiner 自动衔接规则
如果用户引用 converted 文件并说"开始处理"：
1. 检查 `refined/{对应目录}/` 是否已有 *_prd.md 文件
   - 有：提示"已有精化文档，是否直接使用？还是重新精化？"
   - 无：提示"是否先执行需求精化（生成PRD）？建议精化后再进入开发流程"
2. 用户选择精化 → 调用 `requirement-refiner` 技能
3. 用户选择跳过 → 走原流程（状态2开始）

**退出条件**：关键词提取完成 → 进入状态2.5

## 状态2.5：需求分类判定

**触发条件**：关键词提取完成
**读取规则**：`requirement_patterns.md`
**Agent行为**：按以下优先级判定需求类型

### 判定规则（按优先级从高到低）

| 优先级 | 判定条件 | 分类结果 | 进入链路 |
|--------|----------|----------|----------|
| 1 | 提及已有需求ID（如"004"、"002"）+ 变更动词 | 变更需求 | 链路B |
| 2 | 提及已有指标名称 + 变更动词（修改/加/改/删/调整/扩展） | 变更需求 | 链路B |
| 3 | 包含Bug/错误/问题/不对/修复 + 提及已有指标 | 变更需求（Bug修复） | 链路B |
| 4 | 包含"新增/新建/创建/开发" + 未命中任何已有模式 | 全新需求（独立型） | 链路A |
| 5 | 包含"新增" + 命中已有模式 + "基于/参考/类似" | 全新需求（依赖型） | 链路A |
| 6 | 命中已有模式（≥60%）+ 无变更动词 | 全新需求（相似型） | 链路A |
| 7 | 无法判定 | 询问用户 | 等待确认 |

### 变更动词库
```
修改、改、调整、优化、加、新增（字段/逻辑/产品线）、删除、去掉、
修复、修正、扩展、补充、完善、更新
```

### 新建动词库
```
新增（指标/需求）、新建、创建、开发、做一个、统计一个
```

### 判定补充说明：规则差异 ≠ 框架差异
以下情况属于"规则差异"，仍归类为变更需求（链路B），不应升级为全新需求：
- 数据源不同（如管报→GSS）
- 计算公式不同（如BP/LX选择→只取LX）
- 产品线分类规则不同（如内销用PG00003，外销用HX00223）
- 剔除条件不同（如内销剔除gorenje，外销剔除OEM/标机/样机）
- 时间频率不同（如按月→按天）

只有以下情况才视为"框架差异"，可考虑归类为全新需求：
- 数据流转路径发生变化（如不再走DWD→DWS→ADS，改为直接查询）
- 目标表结构发生变化（如需要新建完全不同的表）
- 业务域完全不同（如从IPM切换到IRS）

### 判定后必须向用户确认

**输出模板**：
```
【需求分类判定】

我判断这是一个 [全新需求/变更需求]：
- 类型：[独立型新指标 / 依赖型新指标 / 相似型新指标 / 逻辑变更 / 产品线扩展 / 字段新增 / Bug修复 / 规则变更]
- 指标数量：[单指标 / 多指标（N个）]
- 复杂度预判：[简单 / 复杂 / 复杂+编排]
- 关联需求：[无 / 需求ID]
- 判定依据：[说明为什么这样判定]

请确认是否正确？如果不对请告诉我正确的类型。
```

**退出条件**：用户确认分类正确 → 进入对应链路
- 链路A（多指标）：进入A0
- 链路A（单指标）：直接进入A1
- 链路B：**Agent必须先读取 `etl_change_management.md`**，然后进入B1

## 链路A：新建需求流程

### A0：需求编排【多指标场景自动触发】

**触发条件**：状态2.5判定为多指标（≥2个）且同领域
**读取规则**：`requirement_patterns.md`（依赖字段）
**Agent行为**：
1. 列出所有指标清单
2. 识别指标间的依赖关系和共享层
3. 确定执行顺序（按依赖拓扑排序）
4. 识别跨指标一致性约束

**输出模板**：
```
【需求编排 — 多指标场景】

一、指标清单
| 序号 | 指标名称 | 预判分层 | 预判目标表 | 依赖 |
|------|----------|----------|-----------|------|
| 1 | [指标1] | [DWS+ADS] | [表名] | 无 |
| 2 | [指标2] | [同上/独立] | [表名] | #1（共表） |
| 3 | [指标3] | [DWS+ADS] | [表名] | 无 |

二、共享层识别
- DWD共享：[表名]（指标#X/#Y共用）
- 中间表共享：[表名]（指标#X/#Y共用）
- 无共享层

三、执行批次（按依赖关系）
| 批次 | 包含指标 | 原因 |
|------|----------|------|
| 第一批 | #1 + #2 | 共表，同时设计 |
| 第二批 | #3 | 独立，但被#4依赖 |
| 第三批 | #4 | 依赖#3的输出 |

四、跨指标一致性约束
| 约束项 | 统一方案 | 待确认 |
|--------|----------|--------|
| 产品线分类 | 统一使用PUB-003 | [新产品线的定义？] |
| 时间口径 | [统一/各指标独立] | [待确认] |
| is_project标准 | 各指标独立定义 | — |
| 管理口径 | [统一/区分] | [待确认] |

五、口径一致性矩阵（必做）
| 指标 | "实际值"来源 | 口径含义 | 与其他指标一致？ |
|------|-------------|----------|-----------------|
| [指标1] | [管报/GSS/库存] | [已确认收入/订单量/库存量] | ✅/⚠️ |
| [指标2] | [管报/GSS/库存] | [已确认收入/订单量/库存量] | ✅/⚠️ |

如果存在⚠️（口径不一致），必须说明：
- 具体差异（如：管报=已出货确认收入，GSS=已下单未必发货）
- 是否导致逻辑矛盾（如：有GSS订单但生命周期状态为"研发中"）
- 用户是否接受这种不一致

六、上游就绪度处理策略
当A1发现上游就绪度≠✅时，提供3种选项：
| 选项 | 说明 | 适用场景 |
|------|------|----------|
| A. 先补上游 | 暂停编排，先完成上游补充/修改 | 上游缺失影响核心逻辑 |
| B. 骨架先行 | 先做设计，SQL中标注TODO待上游就绪后填充 | 上游不影响骨架，只影响填充 |
| C. 绕过 | 不依赖该上游，改用替代数据路径 | 有可替代数据源 |

七、执行模式选择
| 模式 | 说明 | 适用场景 |
|------|------|----------|
| 标准模式 | 每批独立走A1~A6b，批次间有检查点 | 指标间差异大、需逐个确认 |
| 快速批次模式 | 一次性输出所有骨架，统一确认后连续生成SQL | 指标间高度相似、用户信任编排 |

快速批次模式触发条件（全部满足才可提议）：
- 所有指标命中同一参考需求或同系列模式
- 口径一致性矩阵中无⚠️项
- 上游就绪度全部为✅
- 用户主动说"一起做"/"快速过"等信号

请确认编排方案。确认后按批次依次进入A1。
```

**退出条件**：用户确认编排方案 → 按第一批进入A1

**批次执行规则**：
- **标准模式**：每批执行完整的 A1→A2→A3→A4a→A4b→A6a→A6b 流程，批次间有检查点
- **快速批次模式**：一次性输出所有批次的A4a骨架 → 统一确认 → 连续执行A4b~A6b → 统一A5
- A5（最终确认）在全部批次完成后统一执行一次
- A7（文档+沉淀）在全部批次完成后统一执行一次

### A1：依赖识别

**触发条件**：需求分类为"全新需求"且用户已确认（单指标直接进入；多指标从A0批次进入）
**读取规则**：`requirement_patterns.md`（依赖字段）
**Agent行为**：
1. 检查新需求是否依赖已有DWS/ADS表
2. 如果是依赖型：识别上游需求和上游表，**递归检查上游就绪度**
3. 如果是相似型：识别参考需求

**输出模板**：
```
【依赖识别】

- 依赖类型：[独立（无上游依赖）/ 依赖型（基于已有表）/ 相似型（参考已有需求）]
- 上游需求：[无 / 需求ID + 表名]
- 上游就绪度：[✅ 已完成稳定 / ⚠️ 有未闭环变更 / ❌ 开发中]
- 参考需求：[无 / 需求ID]

请确认是否正确？
```

**退出条件**：用户确认 → 进入A2

### A2：需求澄清（新建专属）

**触发条件**：A1完成且用户确认
**读取规则**：`etl_analysis_clarification.md`

#### 高完整度快速通道（减少交互轮次）
Agent在进入澄清前，先对用户输入做完整度评分（7维度，满分14分）：
- **≥10分（明确）**：输出"我理解的需求摘要"让用户确认，确认后仍需输出"无额外澄清项"让用户确认进入A3
- **6-9分（基本明确）**：只问缺失的1-2个维度，不逐项过
- **<6分（模糊）**：走完整澄清流程

**注意**：即使完整度≥10分，A2步骤本身不可跳过——必须输出"澄清结论"并获用户确认。

**快速通道例外（强制不跳过）**：
- **相似型需求**：即使完整度≥10分，也必须执行"逐点差异确认"（见下方相似型澄清规则）。原因：相似型的价值在于发现差异，跳过差异确认等于跳过核心步骤
- 此例外下允许跳过其他维度的逐项澄清，但差异确认不可省略

**核心原则：高质量理解需求，减少无效交互。能从上下文推断的不问，能从模式库匹配的不重复确认。**

#### 独立型新需求 — 完整澄清（仅当完整度<6时）
| 序号 | 必问项 | 说明 |
|------|--------|------|
| 1 | 指标名称与业务含义 | 这个指标衡量什么？ |
| 2 | 计算公式 | 分子/分母分别是什么？ |
| 3 | 覆盖产品线 | 冰箱/冷柜/洗衣机/空调/日立/视像？ |
| 4 | 管理口径 | 产品型号口径还是销售型号编码口径？ |
| 5 | 时间粒度 | 月度/年累/近N月滚动？ |
| 6 | 数据来源 | 管报？库存？平台库？ |
| 7 | 特殊规则 | 保护期？剔除条件？ |
| 8 | 时间判定规则 | 时间窗口的边界定义？时变属性如何处理？ |

**时间判定规则子维度（P0级必问，所有涉及时间窗口的需求）**：
当需求涉及"近N月"、"上市N个月内"、"滚动N月"等时间窗口时，必须澄清：
| 子项 | 说明 | 示例 |
|------|------|------|
| 边界定义 | 自然月还是日历天数？含首月/末月？ | "近12月"=包含当月往前推12个月？还是不含当月？ |
| 起点锚定 | 以什么时间为起点？ | 实际上市时间？首次出货时间？审批通过时间？ |
| 时变属性 | 同一对象的标记是否随时间变化？历史数据是否需重算？ | "新品"标记到第13个月自动失效，历史月份是否回刷？ |
| 跨年处理 | 年累指标的年度切换逻辑？ | 1月数据是属于新年还是跟去年12月一起？ |

Agent可根据上下文推断的子项不必追问，但"边界定义"和"时变属性"如果无法推断则必问。

#### 依赖型新需求 — 差异澄清
| 序号 | 必问项 | 说明 |
|------|--------|------|
| 1 | 与上游的关系 | 从上游表筛选？聚合？关联？ |
| 2 | 筛选/聚合条件 | 具体的WHERE或GROUP BY |
| 3 | 新增的业务规则 | 上游没有但本指标需要的规则 |

#### 相似型新需求 — 逐点差异确认
| 序号 | 必问项 | 说明 |
|------|--------|------|
| 1 | 参考需求核心逻辑点列表 | Agent先列出参考需求的5-8个核心逻辑点，用户逐点回答"相同/不同/不确定" |
| 2 | 不同点的新逻辑 | 对标记为"不同"的逻辑点，追问新逻辑是什么 |
| 3 | 新增的维度/指标 | 参考需求没有但本需求需要的 |

2. 如需ALTER TABLE，生成DDL
3. 模式B：生成草稿文件供用户手工合入
4. 模式A：直接str_replace修改正式脚本

**退出条件**：修改完成 → 进入B4.5

#### B4退出信号识别（含跨对话恢复）

| 用户表述 | 上下文线索 | 判定 | Agent行为 |
|----------|-----------|------|-----------|
| "草稿已合入"/"已手工粘贴" | 存在对应草稿文件 | B4已由用户完成 | 先执行B4.5，再进入B5 |
| "闭环"/"收尾"/"完成" | 存在草稿/修改证据 | B4已完成 | 先执行B4.5，再进入B5 |
| "闭环"/"完成" | 无明确变更操作证据 | 歧义 | 快速确认 |
| "不用管了"/"到此为止" | 任何 | 对话结束 | 不进入B5 |

### B4.5：下游影响提醒（必检，在B5之前）

**触发条件**：B4完成确认后、进入B5之前
**Agent行为**：
1. 检查当前需求的脚本分层链路，确认本次修改涉及哪一层
2. 如果修改了DWD或DWS层，检查下游是否需要同步
3. **无论用户是否提及下游，Agent都必须主动输出下游影响提醒**
4. 确认无下游影响 → 直接进入B5

**B4 vs B4.5 的边界**：
- B4覆盖：同一需求核心数据链路上的所有脚本
- B4.5提醒：跨需求或弱关联的下游影响

**退出条件**：用户确认下游处理方式 → 进入B5

### B5：文档更新

**触发条件**：B4完成
**Agent行为**：
1. 更新 changelog.md（记录变更）
2. 更新 requirement.md 头部速查
3. 草稿文件头部标注已合入
4. lineage.md 由Hook自动触发更新
5. 更新 requirement_patterns.md 最后命中时间
6. **自动调用 `interaction-metrics` 技能**
7. **自动调用 `feedback-collector` 技能**
8. **主动改进提醒**
9. **能力包同步检查**：如果本次变更涉及以下任一场景，提醒用户同步：
   - 指标公式/口径变更 → 更新 `metrics/{domain}.yaml` 中的 definition/formula
   - 新建表 → 追加 `catalog.yaml`
   - 发现新的数据源坑 → 追加 `source-systems.yaml`
   - 规则变更（产品线分类/排除条件等）→ 更新 `business-rules/`
   - 聚合方式变更 → 更新 `aggregation-rules.yaml`

   输出格式（仅涉及变更时输出，纯修Bug不输出）：
   ```
   📦 能力包同步：本次变更影响能力包 [N] 处
   - [文件]：[变更说明]
   是否现在同步？（是/否/跳过）
   ```

**退出条件**：文档更新完成 + 度量数据生成完成 + 反馈采集完成（或跳过） + 能力包同步完成（或跳过）→ 进入B6

### B6：下游执行（可选）

**触发条件**：B4.5中用户选择"现在处理"
**Agent行为**：
1. 对每个受影响的下游脚本执行修改（等同于再走一次B4）
2. 所有下游修改完成后，统一在B5中记录

**退出条件**：所有下游修改完成

## 全局规则

### 阶段门禁（Gate）
每个状态的退出都需要用户明确确认。Agent不得在未获确认的情况下进入下一状态。

**绝对不可跳步规则**：无论输入来源多完整（refined/converted/口头描述），链路A的每个步骤（A0~A7）和链路B的每个步骤（B1~B6）必须按顺序逐个执行。不存在"信息足够所以跳过"的情况。输入质量高时，步骤的输出可以简化（如"refined已澄清，无需追问"），但步骤本身、输出动作、用户确认点均不可省略。

确认信号识别：
- 明确确认："确认"、"可以"、"没问题"、"对的"、"正确"、"继续"
- 明确否定："不对"、"不是"、"修改"、"调整" → 停留在当前状态修正
- 模糊回复：追问"请确认是否可以进入下一步？"

### 禁止自动推进规则（Anti-Auto-Advance）

1. 用户确认当前阶段 ≠ 授权进入下一阶段
2. 每个阶段输出结论后，Agent只做两件事：
   a. 展示当前阶段结论
   b. 问"请确认"
3. 用户确认后，Agent必须说明即将进入的下一阶段名称，并询问"是否继续？"或等待用户说"继续"
4. 禁止在同一条回复中同时包含"当前阶段结论"和"下一阶段的输出内容"
5. 唯一例外：用户主动说"继续"/"下一步"/"往下走"时，可直接进入下一阶段并输出

### 回退规则
- 用户在任何阶段说"回到上一步"/"重新来" → 回退到上一状态
- 用户在任何阶段说"取消"/"不做了" → 回到状态1

### 错误处理
- 无法判定需求分类 → 直接询问用户
- 表匹配失败 → 提示用户确认表名
- SQL生成失败 → 说明原因，建议简化
