# ETL变更需求管理规则

## 概述
本文件定义变更需求（链路B）的详细处理规则，包括变更分类、澄清维度、影响分析和修改策略。

## 一、变更类型定义

| 类型代码 | 类型名称 | 描述 | 典型场景 |
|----------|----------|------|----------|
| CHG-01 | 逻辑变更 | 修改计算公式、阈值、判定条件 | "低效阈值从0.8改成0.7" |
| CHG-02 | 产品线扩展 | 已有指标新增一条产品线 | "在销型号数加上厨电" |
| CHG-03 | 字段新增 | 在已有表中新增字段 | "DWS表加一个出点标记字段" |
| CHG-04 | Bug修复 | 已有逻辑有错误需修正 | "冰箱外销CKD剔除逻辑有问题" |
| CHG-05 | 规则变更 | 公共规则变更影响多个需求 | "PUB-003产品线分类规则调整" |
| CHG-06 | 口径调整 | 统计口径或维度变化 | "日立从销售型号改为项目口径" |

## 二、变更澄清维度

### CHG-01 逻辑变更
| 序号 | 必问项 | 说明 | 示例回答 |
|------|--------|------|----------|
| 1 | 修改哪个计算逻辑？ | 定位到具体的CASE/WHERE/公式 | "is_project的判定条件" |
| 2 | 当前逻辑是什么？ | Agent读取SQL后展示，用户确认 | "当前是上市3个月内为保护期" |
| 3 | 新的逻辑是什么？ | 用户描述新规则 | "改为上市6个月内为保护期" |
| 4 | 是否影响ADS层汇总？ | 判断是否需要同步修改ADS | "是/否" |

### CHG-02 产品线扩展
| 序号 | 必问项 | 说明 |
|------|--------|------|
| 1 | 新增哪条产品线？ | 产品线名称 |
| 2 | 产品线分类规则 | 产品大类/中类/小类的CASE条件 |
| 3 | 数据来源 | 与已有产品线相同？还是有新的源表？ |
| 4 | 管理口径 | 产品型号口径还是销售型号编码口径？ |
| 5 | 特殊剔除规则 | 是否有品牌/工厂/类型的剔除条件？ |
| 6 | 库存数据来源 | 库存从哪个表取？（如适用） |

### CHG-03 字段新增
| 序号 | 必问项 | 说明 |
|------|--------|------|
| 1 | 新增什么字段？ | 字段名称和业务含义 |
| 2 | 字段数据类型 | 参考sql_rules.md标准类型映射 |
| 3 | 字段计算逻辑 | 如何计算/从哪里取值 |
| 4 | 是否需要ALTER TABLE？ | 目标表是否已有该字段 |
| 5 | 影响哪些INSERT语句？ | 需要在哪些INSERT中新增该字段 |

### CHG-04 Bug修复
| 序号 | 必问项 | 说明 |
|------|--------|------|
| 1 | 错误现象 | 数据结果哪里不对？ |
| 2 | 期望正确结果 | 应该是什么样的？ |
| 3 | 错误数据样例 | 能否提供具体的错误记录？ |
| 4 | 怀疑的原因 | 用户是否有初步判断？ |

### CHG-05 规则变更
| 序号 | 必问项 | 说明 |
|------|--------|------|
| 1 | 哪条公共规则变更？ | PUB-XXX编号 |
| 2 | 新规则内容 | 完整描述新规则 |
| 3 | 影响哪些需求？ | Agent自动从patterns中查找引用该规则的需求 |
| 4 | 是否需要全部同步？ | 还是只改部分需求？ |

### CHG-06 口径调整
| 序号 | 必问项 | 说明 |
|------|--------|------|
| 1 | 当前口径 | 产品型号/销售型号编码/项目 |
| 2 | 目标口径 | 改为什么口径？ |
| 3 | 影响的产品线 | 全部还是部分产品线？ |
| 4 | 历史数据处理 | 是否需要回刷历史？ |

## 三、影响分析规则

### 下游依赖查找
根据 `requirement_patterns.md` 中的依赖字段，自动识别受影响的下游需求：

```
004 在销型号数
  → 005 在产型号数（依赖004的DWS表）
  → 007 单型号销量（依赖004的型号数作为分母）

005 在产型号数
  → 006 平台数（依赖005的在产型号关联平台）

006 平台数
  → 008 单平台销量（依赖006的平台数作为分母）

007 单型号销量
  → 008 单平台销量（依赖007的销量数据）
```

### 影响等级判定
| 等级 | 条件 | 处理方式 |
|------|------|----------|
| 高 | 修改了DWS表的字段定义或核心计算逻辑 | 必须同步修改所有下游 |
| 中 | 修改了筛选条件但不影响输出字段 | 提示用户确认是否影响下游 |
| 低 | 只修改了注释/格式/非核心字段 | 无需同步 |

## 三点五、交付模式选择【B3确认后、B4执行前必问】

在影响分析确认后、执行修改前，Agent**必须**询问用户选择交付模式：

```
【交付模式选择】

本次变更您希望用哪种交付模式？

A. 直接修改正式脚本（适合简单变更：字段新增、阈值调整等）
B. 草稿→手工合入→Agent验证（适合复杂变更：产品线扩展、多需求联动等）
   - Agent生成副本草稿（_draft.sql）
   - 您验证并手工合入正式脚本（可在合入时优化细节）
   - Agent验证正式脚本中逻辑完整性

请选择 A 或 B：
```

### 模式选择建议（Agent自动推荐）
| 条件 | 推荐模式 | 理由 |
|------|----------|------|
| 变更类型为CHG-01（逻辑变更）且影响≤2个文件 | A | 简单精准修改 |
| 变更类型为CHG-03（字段新增） | A | 明确的ALTER+INSERT修改 |
| 变更类型为CHG-04（Bug修复） | A | 定位明确，快速修复 |
| 变更类型为CHG-02（产品线扩展） | **B** | 逻辑复杂，需验证空间 |
| 涉及≥2个需求联动 | **B** | 影响面大，降低风险 |
| 新增SQL行数预估≥100行 | **B** | 代码量大，需逐步验证 |
| 涉及独立业务规则（库存源/代工判定等） | **B** | 差异点多，用户可在合入时优化 |

### 模式B的执行流程
0. **参考确认（生成前必须执行）**：Agent用grep搜索正式脚本中与本次变更对应的逻辑段落（如搜索目标zhibiao_type、目标产品线、目标in_out_sale），确认参考对象正确。禁止从文件开头顺序读取后直接参考第一个匹配段落。同时重新读取需求文件中对应产品线的规则段落，确保生成时有明确的需求依据。
1. Agent生成副本草稿文件，存放到 `sql_scripts/drafts/` 子目录（命名：`{原文件名}_{变更简称}_draft.sql`）。长脚本输出遵循 `output_safety.md` 中的分段输出规则。
1.5. **轻量自检（生成后自动执行，用户无感）**：Agent对生成的草稿执行以下检查：
   - 对每个产品线的关键筛选字段，查阅 `table_structures.md` 验证字段备注含义是否与需求描述一致
   - 对每个剔除条件，回到需求文件确认是否有此规则（需求中没有的不加）
   - **字段完整性核对**：逐项对照需求文档中列出的所有字段（如"明细字段需求"列表），确认每个字段都在INSERT列表中体现。缺一个就是遗漏
   - **指标完整性核对**：逐项对照需求文档中列出的所有子指标/口径，确认每个都有对应的SQL段落。缺一个就是遗漏
   - **目标表结构验证**：通过MCP查询目标DWS/ADS表的字段列表，确认新增字段是否已存在。不存在的标注 `[需ALTER TABLE]` 并提醒用户
   - **跨层字段一致性验证**：当草稿涉及DWD→DWS或DWS→ADS的数据流转时，验证上游INSERT写入的字段名与下游WHERE/JOIN引用的字段名完全一致。典型断链场景：DWD写入`in_out_sale`但DWS用`model_label_6`筛选。发现不一致时立即修正
   - 不一致的立即修正，无需等用户反馈
1.6. **changelog即时记录**：草稿首次生成后，立即在对应需求的 `changelog.md` 中追加一条记录，状态标记为"🔄 草稿阶段"。合入正式脚本后再更新状态为"✅ 已完成"。避免跨天/跨对话时遗忘。
2. 用户验证草稿逻辑，可提出修改意见（Agent迭代修正草稿）
3. 用户确认草稿无误后，手工将逻辑合入正式脚本（可在合入时进一步优化细节）
4. 用户告知"已合入"，Agent通过grep验证正式脚本中逻辑完整性
5. Agent更新changelog记录闭环

### 模式B的优势（来自厨电案例实践）
- **降低风险**：草稿不影响正式脚本，验证失败可随时重来
- **用户主导权**：用户在合入时可优化细节（如代工判定从"海信"精化为"6516-黄岛厨电工厂"）
- **Agent验证闭环**：合入后Agent自动确认完整性，避免遗漏
- **乱码恢复**：输出过程中出现乱码时，遵循 `output_safety.md` 中的恢复协议

## 三点六、批量输出风险评估【多指标/多脚本场景必须执行】

当一次变更涉及≥3个SQL脚本或≥2个独立指标时，Agent**必须**向用户提示风险并建议拆分：

### 风险提示模板
```
⚠️ 【批量输出风险提示】

本次需求涉及 [N] 个指标 / [M] 个SQL脚本，一次性生成存在以下风险：
1. 注意力衰减：后生成的脚本质量系统性低于先生成的
2. 遗漏风险：多脚本间的关联逻辑容易遗漏（如平台数依赖在产型号）
3. 修正成本高：一个脚本有问题需要重新生成时，可能影响其他已确认的脚本

建议方案：
A. 逐指标生成（推荐）：按依赖顺序逐个生成，每个确认后再生成下一个
   顺序建议：[列出依赖顺序]
B. 一次性生成（风险自担）：我会尽力保证质量，但无法保证后半部分与前半部分同等精度

请选择 A 或 B：
```

### 触发条件
| 条件 | 判定 |
|------|------|
| 涉及≥3个DWS/ADS脚本 | 必须提示 |
| 涉及≥2个独立指标（不同zhibiao_type） | 必须提示 |
| 单个脚本预估≥200行 且 数量≥2 | 必须提示 |
| 涉及跨需求联动（如002+004+006） | 必须提示 |

### 逐指标生成时的依赖顺序建议
按数据流转的上游→下游顺序：
1. 在销型号数（基础型号范围）
2. 在产型号数（从在销筛选）
3. 低效型号占比 + 新品规划命中率（依赖型号范围+销量）
4. 平台库 + 产品平台数（依赖在产型号）
5. 单型号销量（依赖在销型号）
6. 单平台销量（依赖平台数+销量）

### 用户选择B（一次性生成）时的补偿措施
即使用户选择一次性生成，Agent仍须：
1. 按依赖顺序生成（不随机跳跃）
2. 每个脚本生成后立即执行1.5自检，不等全部生成完再检查
3. 生成完毕后，额外做一次**跨脚本一致性检查**：
   - 各脚本中的product_line值是否一致
   - 上游脚本的输出字段是否被下游正确引用
   - 公共CTE（如产品线映射）在各脚本中是否一致

## 三点七、草稿文件隔离规则（防止参考污染）

### 存放位置
所有草稿文件统一存放在 `requirements/{ID}/sql_scripts/drafts/` 目录下，不与正式脚本混放。

### 目录结构
```
requirements/{ID}/sql_scripts/
├── {正式脚本1}.sql          ← 正式脚本（唯一参考对象）
├── {正式脚本2}.sql
├── validate_data_quality.sql
└── drafts/                   ← 草稿隔离目录
    ├── {脚本名}_{变更简称}_draft.sql
    └── {脚本名}_{变更简称2}_draft.sql
```

### 参考规则（强制）
1. **禁止参考草稿**：Agent在生成新草稿时，**禁止**将 `drafts/` 目录下的任何文件作为参考对象
2. **合法参考对象**（仅限以下三类）：
   - `sql_scripts/` 根目录下的正式脚本（无 `_draft` 后缀）
   - 需求文档（`requirement.md`）
   - intake转换文档（`intake/{ID}/converted/*.md`）
3. **合入后处理**：草稿合入正式脚本后，草稿文件保留在 `drafts/` 目录（便于追溯），不删除
4. **命名标识**：草稿文件必须包含 `_draft` 后缀，正式脚本禁止包含此后缀
5. **违规判定**：如果Agent在生成草稿时引用了其他草稿文件的逻辑（而非正式脚本），视为参考污染，必须重新生成

### 迁移说明
已有的 `*_draft.sql` 文件将逐步迁移到 `drafts/` 子目录。迁移前，Agent仍按文件名中的 `_draft` 后缀识别草稿文件，不作为参考对象。

## 四、修改策略

### SQL修改原则
1. **精准修改**：使用str_replace定位到具体位置修改，不重写整个文件
2. **保留注释**：修改时保留原有注释，新增修改注释标记
3. **幂等性**：修改后的SQL仍然满足幂等执行要求
4. **向后兼容**：新增字段使用COALESCE提供默认值
5. **经验-需求冲突检测（变更扩展类必须执行）**：
   - 生成变更SQL时，对于每个"从已有逻辑中借用"的字段/条件/计算方式，必须与 `table_structures.md` 和需求文件做交叉验证
   - 验证不通过的（即经验实现与需求描述或表结构备注矛盾），以需求文件+表结构为准，不以经验为准
   - Agent内部自动执行此检测，无需向用户逐条确认；仅当出现无法自行判定的冲突时才向用户提问
   - 典型冲突场景：
     - 需求说"产品线取XX"，经验用PG00003，但表结构中有专属字段HX00223备注="产品线" → 用HX00223
     - 需求说"品牌不取OEM品牌值"，经验用his_oembrand，但表结构中his_productsbrand备注="品牌名称" → 用his_productsbrand
     - 需求说"按天统计"，经验中有"本月上市置NULL"的逻辑 → 去除该逻辑
   - **禁止模糊匹配替代精确规则**：当需求文档给出了精确的枚举列表（如产品线名称列表、编码列表），禁止用LIKE/正则等模糊方式"简化"。精确列表必须用精确IN条件
   - **禁止省略需求中的新增字段**：需求文档中明确要求的字段（如"焦距"），即使参考对象中没有，也必须在草稿中体现。不存在的字段通过MCP查表确认后标注新增
   - **禁止简化参考对象的SQL结构**：当参考已有产品线的SQL生成新产品线草稿时，必须完整保留参考对象的SQL结构（字段列表、JOIN关系、WHERE条件数量、UNION ALL分支数）。只替换值，不删减条件。如果新产品线的对应值不确定，保留条件结构并标注 `[待确认]`。禁止提前聚合（参考对象保留明细字段的，草稿中也必须保留，不得自行GROUP BY简化）
6. **MCP验证强制触发规则（变更草稿生成前必须执行）**：
   - 以下场景必须先通过MCP查询表结构，禁止凭记忆/假设编写：
     - 需求中提到的字段在目标表中是否存在
     - 需求中提到的源表筛选条件（如产品小类值、产品公司值）在源表中的实际字段名
     - 新增产品线涉及的关联表（如平台库）是否有对应数据、product_line值是什么
   - 查询结果作为生成依据写入草稿注释中，便于用户验证
7. **修改传播检查（每次代码修改后必须执行）**：
   - 执行代码修改后，用grep搜索被修改模式在全文中的所有出现位置，确认是否有遗漏
   - 重点传播检查场景：
     - 时间相关修改 → 搜索所有 DATE_FORMAT / STR_TO_DATE / date_sub，确认是否有关联逻辑需同步
     - 字段相关修改 → 搜索该字段在全文的所有引用位置
     - 逻辑条件修改 → 搜索相同CASE/WHEN模式在其他产品线段落中的出现
   - 一次修改如果影响N处，必须一次性全部修改完毕，不允许只改用户指出的1处而遗漏其余N-1处

### 修改注释规范
在修改位置添加注释：
```sql
-- [CHANGE] 2026-05-15 变更说明（变更类型：CHG-XX）
```

### changelog.md 更新格式

```markdown
| 日期 | 版本 | 变更类型 | 变更描述 | 影响范围 | 变更人 |
|------|------|----------|----------|----------|--------|
```

### requirement.md 头部强制同步规则

每次变更完成（B5步骤）时，Agent**必须**检查并更新 requirement.md 的"当前状态速查"section。

#### 触发条件（满足任一即必须更新头部）
1. 新增或删除了产品线
2. 新增或删除了SQL脚本文件
3. 数据源发生变化（如管报→GSS）
4. 新增了公共规则引用（PUB-XXX）
5. 指标口径(zhibiao_type)有变化
6. 内外销覆盖范围有变化

#### 更新方式
1. 读取最新 changelog 最后一条记录的编号和日期
2. 对照 `sql_scripts/` 下正式脚本文件列表
3. 更新头部速查表中对应字段
4. 更新"最后同步"版本戳为 `changelog #{最新编号}, {日期}`

#### 头部速查格式（标准）
```markdown
## 当前状态速查（最后同步：changelog #NNN, YYYY-MM-DD）

### 覆盖范围
| 维度 | 当前值 |
|------|--------|
| 内销产品线 | [逗号分隔列表] |
| 外销产品线 | [逗号分隔列表，无则写"无"] |
| 指标口径 | [zhibiao_type列表] |
| 实际销量来源（内销） | [管报/GSS/其他] |
| 实际销量来源（外销） | [GSS协议订单/排产单/无] |
| 规划量来源 | [BP+LX/仅LX/其他] |
| 应用公共规则 | [PUB-XXX列表] |

### 脚本清单
```

## 六、变更草稿生成强制规则（防止经验覆盖需求）

### 问题背景
产品线扩展（CHG-02）场景中，Agent倾向于"复制参考对象+微调"，导致以下系统性错误反复发生：
- 需求有精确规则，Agent用模糊匹配简化
- 需求有新增字段，Agent因参考对象没有而遗漏
- 需求有独立子指标，Agent因参考对象合并处理而遗漏
- 需求涉及关联表，Agent因参考对象不涉及而跳过

### 强制执行清单（生成草稿前逐项过）

#### A. 需求完整性检查（对照需求文档）
```
□ 需求中列出的所有子指标，是否每个都有对应SQL段落？
□ 需求中列出的所有明细字段，是否每个都在INSERT字段列表中？
□ 需求中列出的所有筛选条件/规则，是否每个都在WHERE/CASE中体现？
□ 需求中列出的所有产品线/维度，是否每个都有对应的product_line值？
□ 需求中提到的"同XX"，是否已确认XX的具体逻辑并完整复制？
```

#### B. 精确性检查（禁止模糊替代精确）
```
□ 产品线划分：需求给了枚举列表 → 必须用IN精确匹配，禁止LIKE
□ 产品小类筛选：需求给了具体名称 → 必须用IN精确匹配
□ 字段备注：全部统一为中文，不混用英文
□ 逻辑条件：需求给了具体阈值/公式 → 必须原样使用，不简化
```

#### C. 表结构验证（必须MCP查询，禁止假设）
```
□ 目标DWS/ADS表是否有需求中要求的新字段？→ MCP查询确认
□ 源表中需求提到的筛选值（如产品公司名称）对应哪个字段？→ MCP查询确认
□ 关联表（如平台库）中是否有新产品线的数据？product_line值是什么？→ MCP查询确认
□ 新增字段的数据类型应该是什么？→ 参考sql_rules.md标准类型映射
```

#### D. 差异分析（参考对象 vs 新需求）
```
□ 参考对象有但新需求没有的逻辑 → 不加（如能效机转换，激光不涉及）
□ 新需求有但参考对象没有的逻辑 → 必须加（如焦距字段、平台库关联）
□ 参考对象和新需求都有但规则不同的 → 以新需求为准（如产品线划分规则）
□ 参考对象中的"简化写法" → 检查是否适用于新需求（如LIKE vs IN）
```

### 违规判定
如果草稿中出现以下任一情况，视为违规，必须修正后才能交付：
1. 需求文档中有精确枚举，草稿中用了LIKE/正则
2. 需求文档中列出了N个字段/指标，草稿中只有N-1个
3. 涉及表结构问题但没有MCP查询记录
4. 参考对象的逻辑与需求矛盾但草稿中沿用了参考对象
