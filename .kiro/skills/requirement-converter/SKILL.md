# 需求转换技能

## 触发词
用户说以下任意一种时激活本技能：
- "转换需求"、"整理需求"、"格式化需求"
- "把这个需求转成md"、"标准化一下"
- "收纳需求"、"预处理需求"

## 技能说明
将原始需求输入（粘贴文本、CSV内容、口头描述、会议纪要等）转换为标准化的 .md 文件，按需求分目录存放到 `intake/{需求ID}-{简称}/` 下。本技能只做**格式标准化和信息提取**，不做业务判定、不做表匹配、不做澄清提问。

**核心原则：完整转换，不增不减。** 本技能的目的是把用户的需求文件转换成可读性强的 Markdown 文件。除用户特殊要求外，必须完全转换源文件的所有信息，不可根据自己的理解增加或减少任何内容。源文件有什么就转什么，缺失的标记 `[待澄清]`，多余的不自行补充。

## 职责边界

### ✅ 做的事
- 从散乱信息中提取结构化字段（指标名、产品线、公式等）
- 按统一模板输出 .md 文件
- 对明确的事实直接填入
- 对缺失或模糊的信息标记 `[待澄清]`
- 保留原始输入内容（放入"原始素材"区）

### ❌ 不做的事
- 不判定需求类型（新建/变更/修复）— 留给正式流程
- 不做需求澄清（不向用户提问补充信息）
- 不做数据表匹配
- 不做分层识别
- 不做 SQL 生成
- **不参考历史需求文档**：除非用户额外指定参考，否则禁止读取或参考任何已有的 intake/converted 或 requirements 下的文档。即使指标名称相同，输入模板也可能不同，参考历史会造成干扰

### ⚠️ 强制规则
1. **严格逐步确认**：每一步必须等用户明确确认后才执行下一步，绝不抢跑。未确认不写文件。
2. **准确度第一**：只从用户当次提供的原始内容中提取信息，不推断、不补充、不参考历史。缺失的信息标记 `[待澄清]`，不自行填充。
3. **字段完整性**：源文件中的每一个表头/字段都必须在输出中完整体现，不可因为"多条产品线相同"就省略到公共区域而在各产品线中遗漏。每条产品线/模块必须独立列出所有字段。
4. **格式适配Markdown**：输出格式必须适配Markdown的可读性。对于多字段、多层级的内容，使用"标题 + 加粗字段名 + 缩进列表"格式，而非三列宽表格。复杂内容用子列表展开。
5. **不增不减**：禁止根据自己的理解增加源文件中没有的信息，也禁止省略源文件中存在的信息。转换是格式变换，不是内容加工。
6. **原始文件强制归档**：用户提供的所有原始输入（包括但不限于 .md/.txt/.csv/.xlsx/.xls/.pdf/.png/.jpg/.gif/.pptx/.docx 文件、文件夹、截图等），无论其当前位于项目根目录还是其他非 intake 位置，都必须在转换完成前迁移到对应需求目录的 `raw/` 子目录中。禁止在 intake 以外的位置留下需求相关的原始素材。

## 执行步骤

### 步骤1：接收原始输入

**推荐输入方式（方案五：粘贴+逐项确认，准确率~97%）：**
1. 用户从Excel选中数据区域 → Ctrl+C → 粘贴到聊天框
2. 原始文件（CSV/Excel）另存到 raw/ 目录做归档
3. Agent解析后逐产品线/逐模块输出关键字段摘要，用户逐个确认

**输入提醒规则：**
如果用户只提供了CSV/Excel文件（通过 `#` 引用或放入raw/），没有在对话中粘贴内容，Agent必须主动提醒：
```
提醒：纯文件读取的准确率约70%（编码问题+合并单元格结构丢失），建议你从Excel中选中数据区域直接粘贴到聊天框，我解析后会逐项跟你确认，准确率可达97%。

如果不方便粘贴，我也可以先从文件解析，但解析完成后需要你逐项核对关键字段。
```

用户通过以下方式提供原始需求：
- **首选**：直接在聊天中粘贴Excel内容（Ctrl+C粘贴）
- 备选：引用 `#intake/{YYYYMMDD}-{简称}/raw/xxx` 文件（需配合逐项确认）
- 备选：截图辅助（结构复杂时补充）
- 口头描述

### 步骤1.5：确定需求目录
- 目录命名格式：`intake/{YYYYMMDD}-{英文简称}/`
- 日期为收纳当天，简称用英文概括指标含义
- 与 `requirements/` 编号无关，intake 是独立的收纳区
- 原始文件存入 `raw/` 子目录，转换文档存入 `converted/` 子目录

### 步骤2：信息提取
从原始输入中识别并提取以下字段（能提取多少提取多少）：

| 字段 | 提取规则 |
|------|----------|
| 指标名称 | 寻找名词性短语（如"低效型号占比"、"单型号销量"） |
| 业务含义 | 寻找"用于/衡量/反映"等描述性语句 |
| 计算公式 | 寻找"=/÷/除以/占比"等数学表达 |
| 产品线 | 寻找"冰箱/冷柜/洗衣机/空调/日立/视像"等产品词 |
| 统计口径 | 寻找"产品型号/销售型号编码/项目"等口径词 |
| 时间粒度 | 寻找"月度/年累/近N月/滚动"等时间词 |
| 数据来源 | 寻找"管报/库存/BP/LX/MDG/PLM"等系统词 |
| 特殊规则 | 寻找"剔除/排除/保护期/阈值"等条件词 |

### 步骤3：生成标准化 .md
按照下方模板生成文件，写入 `intake/{需求ID}-{简称}/converted/{YYYY-MM-DD}_{简述}.md`

### 步骤3.5：原始文件强制归档

**规则（不可跳过）**：转换过程中涉及的所有原始输入文件，必须归档到 `intake/{YYYYMMDD}-{简称}/raw/` 目录下。

**归档范围**：
- 用户通过 `#` 引用的文件
- 用户在对话中提到的项目内文件（如"根目录下的XXX"）
- 用户拖入的图片/文档附件（记录文件名，提示用户手动移动）
- 本次需求相关的所有散落文件（Agent需主动扫描识别）

**归档操作**：
1. Agent识别所有需要归档的文件（含图片、Excel、PDF、文件夹等）
2. 使用工具将文件移动到 `intake/{YYYYMMDD}-{简称}/raw/` 下
3. 如果文件无法自动移动（如用户拖入的附件），明确提示用户：
   ```
   请将以下文件手动移动到 intake/{YYYYMMDD}-{简称}/raw/：
   - {文件1}
   - {文件2}
   ```
4. 移动完成后在 converted 文件的 front-matter `source_file` 中记录所有原始文件路径

**移动文件防丢失规则（强制）**：
Move-Item操作本身不会丢失文件内容，但当文件在编辑器中处于打开状态时，编辑器可能在检测到原路径文件消失后，将空内容保存到新路径，覆盖已移动的文件。必须遵守以下规则：

1. **移动前**：提醒用户关闭编辑器中已打开的源文件标签页：
   ```
   ⚠️ 请先关闭编辑器中以下文件的标签页，再确认执行移动：
   - {文件1}
   - {文件2}
   关闭后回复"已关闭"，我再执行移动。
   ```
2. **移动时**：先创建目标目录（`New-Item -ItemType Directory -Force`），再执行 `Move-Item`
3. **移动后**：立即用 `Get-Item` 检查目标文件的 Length 是否 > 0。如果为0字节，说明被编辑器覆盖了，需要用 `fs_write` 从上下文中恢复内容
4. **整个文件夹移动**：优先移动整个文件夹（`Move-Item {源文件夹} {目标路径}`），而非逐个文件移动，减少编辑器干扰的概率
5. **禁止使用Copy-Item+删除源文件**的方式替代Move-Item（Copy-Item对含中文路径的文件可能有编码问题）

**主动扫描规则**：
- 执行步骤1接收输入时，Agent检查项目根目录和 `文件输出/` 等常见临时目录，识别与当前需求相关的散落文件
- 识别依据：文件名包含需求关键词（如指标名称、日期等）
- 发现散落文件时主动提示用户确认是否归档：
  ```
  发现以下文件可能属于本次需求，是否一并归档到 raw/ 目录？
  - {根目录}/项目按计划实施率-PRD.md
  - {根目录}/image.png（如果与需求相关）
  请确认：全部归档 / 选择性归档 / 跳过
  ```

### 步骤3.7：逐项确认（多产品线/多模块需求必做）

当需求涉及多个产品线或多个独立模块时，Agent必须在生成最终文档前逐个输出关键字段摘要，等待用户确认：

**确认模板：**
```
【{产品线/模块名}】请确认：
- 业务系统：{值}
- 时间起点：{值}
- 目标规则：{值}
- 剔除条件：{值}
- 实际销量来源：{值}
正确？(Y / 指出错误)
```

**规则：**
- 每次最多展示3个产品线的摘要，避免信息过载
- 用户确认"Y"后继续下一批
- 用户指出错误时立即修正，修正后再次确认
- 全部确认通过后才写入最终 converted 文件
- 单产品线/单模块的简单需求可跳过此步骤

### 步骤4：输出确认
向用户展示生成的文件路径和内容摘要，并提示下一步精化选项：
```
✅ 需求文档已转换完成：intake/{YYYYMMDD}-{简称}/converted/{文件名}.md

提取到的信息：
- 指标名称：XXX
- 指标数量：N个
- 产品线：XXX
- 待澄清项：N 项

下一步建议：
A. 生成精化文档（PRD）— 映射表字段、标注确定度、生成参考指令（推荐）
B. 直接进入开发流程 — 适合简单/单指标需求，跳过精化
C. 稍后处理 — 文件已保存，随时可以回来

请选择：
```

用户选择后的行为：
- **选A**：调用 `requirement-refiner` 技能，生成 `refined/{需求目录}/*_prd.md`
- **选B**：提示用户引用 converted 文件 + "开始处理"进入正式流程
- **选C**：结束当前对话，文件已保存

## 注意事项
- 本技能不启动正式的 ETL 对话流程
- 转换完成后用户可以立即启动正式流程，也可以稍后再处理
- 如果用户同时提供了多个需求，每个需求生成独立的 .md 文件
- 原始文件如果是用户通过 `#` 引用的，记录 source_file 字段

## 格式规范（经验总结）

### 多产品线/多模块内容的格式
当需求涉及多条产品线且每条有独立规则时，使用以下格式：

```markdown
#### {产品线名称}

**{大类名称1}**（如"型号总数取值"）

- **字段A**：值
  - 子项1
  - 子项2
- **字段B**：值
- **字段C**：值

**{大类名称2}**（如"销量取值"）

- **字段D**：值
- **字段E**：值
  - 子项1
  - 子项2
```

### 禁止的格式
- ❌ 三列表格（大类|字段|值）— 单元格内容过长时可读性极差
- ❌ 把各产品线共同字段提取到"公共规则"而在各产品线中省略 — 导致字段遗漏

### 字段完整性检查
输出前必须自检：源文件的每一个表头（如Excel的B列C列表头）是否在每条产品线中都有对应输出。缺一个就是遗漏。
