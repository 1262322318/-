# 激光产品效率管理 — 案例分析

> 日期：2026-05-29
> 类型：产品线扩展（CHG-02）
> 涉及指标：7个（在销型号数、在产型号数、低效型号占比、新品规划命中率、产品平台数、单型号销量/销额、单平台销量）

---

## 一、全流程回顾：从 intake 到 refined 到脚本开发

### 1.1 阶段一：intake（需求接收与标准化）

**输入**：业务方提供的原始需求文档（Word/截图混合格式）

**处理**：通过 requirement-converter 技能转换为标准化 markdown 文件

**产出**：`intake/20260529-laser-product-efficiency/converted/2026-05-29_激光产品效率指标.md`

**关键内容**：
- 7个指标的业务定义
- 产品线映射表（12个编码→激光家用/激光商用/其他）
- 公共范围条件（产品公司=激光显示，产品小类=激光电视/家用投影/商用投影）
- 外销库存筛选条件（3个源表+产品线值）
- 明细字段需求（内销/外销、品牌、销售渠道、焦距）
- 大量"同视像"的引用

**intake阶段的价值**：
- 将非结构化输入转为结构化文档
- 识别出8个待澄清项
- 建立了与已有需求（002~008）的关联关系

---

### 1.2 阶段二：refined（需求精化/PRD生成）

**输入**：intake标准化文档 + 用户交互确认

**处理**：通过 requirement-refiner 技能生成PRD级别文档

**产出**：`refined/20260529-laser-product-efficiency/2026-05-29_激光产品效率管理_prd.md`

**refined文档的核心结构**：

| 章节 | 内容 | 对开发的价值 |
|------|------|-------------|
| 执行摘要 | 全貌速查（7指标、处理顺序、依赖关系） | Agent一次性理解全局 |
| 全局公共规则 | 产品范围、产品线划分、剔除规则、明细字段、时间字段 | 每个指标生成时的强制约束 |
| 指标定义×7 | 每个指标的参考来源、业务规则、强制约束清单 | 自包含，不依赖上下文记忆 |
| 参考指令汇总 | 各指标的grep定位、公共差异、特有差异 | Agent精准定位参考段落 |
| 待澄清项 | 3项已全部确认 | 无阻塞项 |

**refined阶段的关键设计决策**：

1. **字段映射到具体表和备注**：不再说"产品公司字段"，而是明确 `his_pmdproductaffiliatedcompany`（备注：创建公司）
2. **确定度标记**：每个规则标注"确定"，消除歧义
3. **强制约束清单**：每个指标列出必须满足的约束（如"INSERT字段列表必须包含焦距"）
4. **全局禁止行为**：6条禁令防止Agent犯已知错误
5. **差异对照表**：参考对象 vs 本需求的逐项对比

### 1.3 阶段三：脚本开发（草稿生成）

**输入**：refined PRD文档

**流程**：
1. 用户引用refined文档 → 触发refined快速接入规则
2. 跳过状态1~2.5（PRD已包含分类判定）
3. 直接进入B3.5交付模式选择
4. 用户选择：逐指标生成 + 模式B（草稿→手工合入）
5. 按依赖顺序逐个生成7个指标的草稿

**产出**：8个草稿文件

**开发过程中的用户修正（共4次）**：

| 序号 | 用户反馈 | 修正内容 | 影响范围 |
|------|----------|----------|----------|
| 1 | 产品线判定不要用EXISTS | 改为GROUP_CONCAT + LIKE | 全部指标 |
| 2 | 激光是激光事业部 | business_division改为'激光事业部' | 全部指标 |
| 3 | BP/LX的product_line是'激光' | 从IN ('激光家用','激光商用')改为='激光' | 指标3、4 |
| 4 | LIKE '%商用%'改为'%激光-商用产品线%' | 更精确的匹配 | 全部指标 |

**关键观察**：4次修正全部是"业务知识细节"（事业部名称、中间表的product_line值、产品线名称的精确写法），而非结构性错误或遗漏。这与之前的激光开发形成鲜明对比。

## 二、问题回顾：之前激光开发质量差的根因分析

### 2.1 之前的问题清单（来自 etl_change_management.md 经验教训记录）

| 日期 | 错误类型 | 具体描述 | 严重度 |
|------|----------|----------|--------|
| 2026-05-28 | 模糊替代精确 | 产品线划分用LIKE '%商用%'替代精确IN列表 | 高 |
| 2026-05-28 | 遗漏子指标 | 缺失新品规划命中率（独立zhibiao_type） | 高 |
| 2026-05-28 | 遗漏新增字段 | 需求要求焦距字段，草稿中未体现 | 中 |
| 2026-05-28 | 遗漏关联表 | 平台数缺失平台库逻辑 | 高 |
| 2026-05-28 | 未查表结构 | 未通过MCP确认目标表字段 | 中 |
| 2026-05-28 | 简化参考对象结构 | 外销库存3个UNION ALL分支被简化 | 高 |

### 2.2 根因分析

**核心问题**：Agent在没有PRD文档的情况下，依赖"复制参考对象+微调"的策略生成草稿。这种策略的系统性缺陷：

```
参考对象（视像科技）的逻辑
    ↓ Agent复制
激光草稿
    ↓ 但是
需求中的差异点被遗漏（因为Agent的注意力在"复制"而非"对照需求"）
```

**具体失败模式**：

1. **经验覆盖需求**：Agent看到参考对象没有焦距字段，就不加焦距字段——即使需求明确要求
2. **模糊简化**：Agent看到需求说"包含商用→激光商用"，就用LIKE '%商用%'——忽略了精确编码列表
3. **合并处理**：Agent看到低效型号和新品命中率在同一个脚本中，就只生成一个段落——忽略了它们是独立的zhibiao_type
4. **跳过验证**：Agent没有通过MCP查询目标表是否有新字段——直接假设有

### 2.3 之前的对话模式（无refined）

```
用户：引用intake文档，开始处理
Agent：（读取intake）→ 关键词提取 → 分类判定 → 澄清（多轮）→ 生成SQL
                                                    ↑
                                              这里的澄清是碎片化的
                                              Agent的"理解"分散在多轮对话中
                                              生成SQL时已经"忘记"了部分细节
```

## 三、refined模块如何解决这些问题

### 3.1 解决方案的设计思路

refined模块的核心理念：**将分散在多轮对话中的需求理解，固化为一份结构化的PRD文档，作为SQL生成时的唯一权威参考。**

```
之前：intake → 多轮对话澄清 → Agent记忆中的理解 → 生成SQL（容易遗漏）
现在：intake → refined PRD（固化理解）→ Agent每次生成时重新读取PRD → 生成SQL（有据可查）
```

### 3.2 refined文档的6个防错机制

| 机制 | 解决的问题 | 具体实现 |
|------|-----------|----------|
| 强制约束清单 | 遗漏字段/指标 | 每个指标列出必须满足的checklist |
| 全局禁止行为 | 模糊替代精确 | 明确禁止LIKE替代枚举、禁止省略字段 |
| 字段映射表 | 字段名错误 | 每个字段标注所在表+备注+确定度 |
| 差异对照表 | 经验覆盖需求 | 逐项列出参考对象vs本需求的差异 |
| 参考段落定位 | 参考错误段落 | 给出grep命令精确定位 |
| 自包含原则 | 跨指标遗漏 | 每个指标独立，不引用"见上文" |

### 3.3 本次开发的效果对比

| 维度 | 之前（无refined） | 本次（有refined） | 改善 |
|------|-------------------|-------------------|------|
| 结构性错误 | 6个（遗漏指标/字段/关联表） | 0个 | 100%消除 |
| 用户修正次数 | >10次（含重新生成） | 4次（均为业务细节） | 减少60%+ |
| 修正类型 | 结构性+细节性混合 | 仅细节性（事业部名称、字段值） | 质的提升 |
| 生成轮次 | 多次重新生成 | 一次通过（逐指标） | 效率翻倍 |
| 用户信任度 | 低（需逐行检查） | 高（只需确认业务细节） | 显著提升 |

### 3.4 为什么本次仍有4次修正？

这4次修正属于**refined文档本身未覆盖的"运行时知识"**：

1. **事业部名称**（'激光事业部'）：PRD中未明确写出，因为intake原始需求也没提
2. **BP/LX中间表的product_line值**（'激光'）：这是中间表的实际数据值，需要查表才能确认
3. **产品线名称的精确写法**（'激光-商用产品线'）：PRD中写了编码PC00057017，但实际字段存的是汉字名称
4. **产品线判定的SQL写法**（GROUP_CONCAT vs EXISTS）：这是实现层面的偏好

这些修正说明：refined解决了"需求理解"层面的问题，但"实现细节"层面仍需用户参与。这是合理的——模式B（草稿→手工合入）的设计初衷就是让用户在合入时优化细节。

## 四、流程改进建议

### 4.1 已验证的最佳实践

1. **refined文档是产品线扩展的必备前置**：7个指标、多个差异点的场景，没有PRD文档几乎不可能一次性生成正确
2. **逐指标生成优于一次性生成**：按依赖顺序逐个确认，避免注意力衰减
3. **模式B（草稿）适合复杂变更**：用户可以在合入时优化细节，Agent做完整性验证
4. **MCP验证不可省略**：表结构、字段存在性必须实时查询

### 4.2 可进一步优化的点

| 优化点 | 当前状态 | 建议 |
|--------|----------|------|
| 事业部名称 | PRD未覆盖 | refined模板增加"事业部"字段 |
| 中间表product_line值 | 需用户告知 | 生成前自动MCP查询BP/LX表中的product_line枚举值 |
| 产品线字段存储格式 | PRD写了编码 | refined模板增加"字段存储格式"列（编码/汉字） |
| SQL实现偏好 | 用户逐次纠正 | 在refined中增加"实现偏好"section |

## 五、结论

### 5.1 refined模块的核心价值

> **将"需求理解"从Agent的短期记忆中解放出来，固化为可反复引用的结构化文档。**

这解决了产品线扩展场景中最大的痛点：Agent在生成第N个指标时，已经"忘记"了第1个指标澄清时确认的规则。

### 5.2 数据支撑

- 之前激光开发：6个结构性错误 + >10次修正 + 多次重新生成
- 本次激光开发：0个结构性错误 + 4次细节修正 + 一次通过

**质量提升率**：结构性错误从6个降为0个（100%消除）

### 5.3 适用场景

refined模块特别适合以下场景：
- 产品线扩展（多指标、多差异点）
- 跨需求联动变更
- "同XX"引用较多的需求（需要明确"同"的具体含义）
- 新增字段/新增关联表的变更

对于简单变更（阈值调整、Bug修复），refined可能过重，直接走链路B即可。
